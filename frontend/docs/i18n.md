# Internationalization (i18n)

The frontend uses [`i18next`](https://www.i18next.com/) and [`react-i18next`](https://react.i18next.com/) for translating UI copy. This document covers the app's UI strings — for translating the Markdown guides under `docs/`, see `docs/i18n/README.md` instead; that is a separate, documentation-only system.

## How it's wired up

- `src/i18n/index.ts` initializes `i18next`, registers every locale's `translation.json`, and reads/writes the active language to `localStorage` under `accord_language`.
- `src/main.tsx` imports `./i18n` for its side effect (running `i18n.init()`) before the app renders.
- Components call `useTranslation()` from `react-i18next` and read strings with `t("namespace.key")`.
- `src/components/LanguageSwitcher.tsx` is a `<select>` that calls `i18n.changeLanguage()` and persists the choice; it's rendered in `App.tsx`'s header.

## Locale files

Each locale is a flat-ish JSON file at `src/i18n/locales/<code>/translation.json`, grouped by the area of the UI it covers (`nav`, `header`, `notifications`, …). `en` is the source of truth; every other locale must have the same key paths.

Currently shipped:

- `en` — English (fallback)
- `es` — Spanish (proof-of-concept locale)

### Adding a new locale

1. Copy `src/i18n/locales/en/translation.json` to `src/i18n/locales/<code>/translation.json` and translate each value. Keep every key identical to `en` — a missing key falls back to the English string at runtime, which is easy to miss.
2. Import and register it in `src/i18n/index.ts`:
   ```ts
   import xx from "./locales/xx/translation.json";
   // ...
   resources: { en: { translation: en }, es: { translation: es }, xx: { translation: xx } },
   ```
3. Add it to `SUPPORTED_LANGUAGES` in the same file so it shows up in the language switcher.
4. Interpolated strings use `{{variable}}` (e.g. `"unread": "{{count}} unread"`), called as `t("notifications.unread", { count: 3 })`.

### Adding a new string

1. Add the key to `src/i18n/locales/en/translation.json` first.
2. Add the same key, translated, to every other locale file. A string that only exists in `en` still works everywhere (i18next falls back to `en`), but leaving it untranslated defeats the point — treat it as a TODO.
3. Use it via `const { t } = useTranslation(); … {t("your.new.key")}`.

## Current extraction scope

This is the initial pass, not a full sweep of the app: the header/nav (`App.tsx`), the shared `PageState` component's default "Retry" label, and the notification center (`NotificationCenter.tsx`) are wired through `t()`. Most page bodies and modals are still hardcoded English. When you touch a component, prefer extracting the strings you're already editing into the locale files rather than leaving a new hardcoded string behind.

One known gap: notification center entries (`src/lib/notificationCenter.ts`) store a fully-rendered English `title`/`body` at the moment they're created, not a translation key. Changing the active language does not retroactively translate notifications already in the log — only newly created ones would, if `useNotifications.ts` is updated to store keys/params instead of rendered text.

## RTL layout

`src/i18n/index.ts` keeps `<html dir>` and `<html lang>` in sync with the active language (on init and on every `languageChanged` event), based on a small `RTL_LANGUAGES` set (`ar`, `he`, `fa`, `ur`). `ar` (Arabic) is the shipped RTL proof-of-concept locale.

Setting `dir` on `<html>` is necessary but not sufficient — Tailwind's **physical** utilities (`ml-*`, `mr-*`, `pl-*`, `pr-*`, `left-*`, `right-*`, `text-left`, `text-right`, `rounded-l-*`, `rounded-r-*`) do not flip with `dir`. Tailwind's **logical** utilities do (`ms-*`/`me-*`, `ps-*`/`pe-*`, `start-*`/`end-*`, `text-start`/`text-end`, `rounded-s-*`/`rounded-e-*`), because they map to CSS logical properties (`margin-inline-start`, `inset-inline-end`, …). New layout code should prefer the logical utilities so it works in both directions without extra effort.

For a directional icon (an arrow that means "back" or "forward"), mirror it under `rtl:` — e.g. `<ArrowLeft className="rtl:-scale-x-100" />` (see `src/pages/OwnerProfilePage.tsx`).

**Audit scope**: this pass converted the header/nav (`App.tsx`), the notification center dropdown (`NotificationCenter.tsx`), and the owner-profile back link (`OwnerProfilePage.tsx`) as the representative fix. The rest of `frontend/src/` still uses physical Tailwind utilities throughout (modals, cards, charts, page layouts) and has not been swept — treat any component you touch as a candidate to convert its directional classes to logical ones.

## Locale-aware number, date, and token formatting

`src/lib/formatters.ts` holds the primitives:

- `getActiveLocale()` — the active i18next language tag.
- `formatNumber(value, options?, locale?)` — wraps `Intl.NumberFormat`.
- `formatDate(value, options?, locale?)` — wraps `Intl.DateTimeFormat`.
- `formatDigitsForLocale(integerDigits, fractionDigits, locale?)` — re-applies the locale's grouping/decimal *separator characters* to an already-exact digit string. Token amounts can exceed `Number.MAX_SAFE_INTEGER`, so they're built as exact strings from `BigInt` math (see `formatCurrency` in `src/lib/soroban.ts`) and never round-tripped through a JS `number` — this function only swaps which characters mean "thousands" and "decimal point" for the active locale. Digit glyphs themselves stay Western (0-9) even for locales like `ar` that have native numerals — financial amounts favor universal digit recognition over native numeral systems.

`soroban.ts`'s `formatDeadline`, `formatCurrency`, `formatTimeSeriesLabel`, and `formatAnalyticsDate` all take an optional trailing `locale` parameter that defaults to `getActiveLocale()`, so existing call sites are unaffected (and existing tests, which run with the default `en` locale, see identical output) while anything rendered after a language switch picks up the new locale automatically.

**Audit scope**: the shared formatters in `soroban.ts` are the main value here — most call sites didn't need changes since they just call these functions. Chart-specific or ad-hoc `toFixed()`/`toLocaleString("en-US", …)` calls elsewhere (e.g. a couple of spots in `src/components/CreateRecurringPaymentModal.tsx`, `src/lib/forecast.ts`) were not converted in this pass.

## Testing a locale manually

Switch languages from the header dropdown, or set it before load:

```js
localStorage.setItem("accord_language", "es");
```
